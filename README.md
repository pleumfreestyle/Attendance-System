# ระบบลงชื่อเข้า-ออกงานสำหรับบุคลากร

ระบบเว็บแบบ Static frontend (GitHub Pages) เชื่อมต่อ Cloudflare Worker API และ Cloudflare D1 สำหรับเก็บข้อมูลจริง

## ฟังก์ชันที่พัฒนาใน branch นี้

- สมัครบัญชีบุคลากร โดยบัญชีใหม่เริ่มต้นเป็นสถานะรออนุมัติ
- เข้าสู่ระบบด้วยรหัสผ่านที่แฮชด้วย PBKDF2-SHA-256 และ token ที่มีวันหมดอายุ
- ลงเวลาเข้า/ออกโดยส่งพิกัด GPS ให้ backend ตรวจสอบระยะจากสถานที่ทำงานและบันทึกเวลาเซิร์ฟเวอร์
- ดูประวัติลงเวลา ประวัติคำขอลา และสรุปจากรายการที่บันทึกจริง
- ส่งคำขอลาและให้ผู้ดูแลอนุมัติ/ปฏิเสธ
- จัดการบัญชีบุคลากร บทบาท สถานที่ทำงาน รัศมีพื้นที่ และกะทำงาน
- ส่งออกรายงานการลงเวลาเป็น CSV
- เปลี่ยนรหัสผ่าน และส่งคำขอรีเซ็ตรหัสผ่านให้ผู้ดูแลตรวจสอบ
- บันทึก audit log สำหรับการเปลี่ยนแปลงสำคัญ

## โครงสร้าง

- `app.js`, `index.html`, `style.css`: frontend
- `cloudflare/worker.js`: API
- `cloudflare/schema.sql`: ตารางและดัชนีที่ใช้กับระบบ
- `cloudflare/migrations/20261020_token_version.sql`: เพิ่ม token version เพื่อยกเลิก session เก่าหลังเปลี่ยน/รีเซ็ตรหัสผ่าน

## สถานะฐานข้อมูล

การเปลี่ยนแปลงแบบเพิ่มตาราง/ดัชนีสำหรับ `work_locations`, `shifts`, `leave_requests`, `password_reset_requests` และดัชนีที่เกี่ยวข้อง ถูกนำไปใช้กับ D1 แล้วเมื่อ 2026-10-20 ส่วนคอลัมน์ `personnel.token_version` ก็ถูกเพิ่มผ่าน migration แยกแล้ว การเปลี่ยนแปลงนี้ไม่ได้ลบข้อมูลเดิม

## ข้อกำหนดก่อนนำ Worker ขึ้นใช้งานจริง

**อย่านำ `cloudflare/worker.js` ไปแทน Worker ที่ใช้งานอยู่โดยตรงจนกว่าจะรวมเส้นทาง LINE เดิมเข้าด้วยกันและทดสอบครบ** เพราะ Worker ที่อยู่ใน branch นี้ยังไม่มีเส้นทาง `/webhook` และ `/test-send` เดิม การแทนที่ทันทีอาจทำให้ LINE bot หยุดทำงาน

1. สำรอง D1 ก่อนการเปลี่ยนแปลงหรือ deploy ทุกครั้ง
2. ตรวจสอบว่า Worker ผูก D1 ด้วย binding ชื่อ `DB`
3. ตั้งค่า Worker secret `JWT_SECRET` เป็นค่าสุ่มที่คาดเดายากอย่างน้อย 32 ตัวอักษร ห้ามใส่ใน frontend หรือ commit ลง Git
4. สมัครบัญชีแรกด้วยหน้าเว็บ จากนั้นตรวจสอบอีเมลของบัญชีใน D1 และยกระดับบัญชีที่ยืนยันตัวตนแล้วเป็นแอดมินผ่าน Cloudflare D1 Console เท่านั้น เช่น:

   ```sql
   UPDATE personnel
   SET role = 'admin', is_active = 1
   WHERE email = 'REPLACE_WITH_VERIFIED_ADMIN_EMAIL';
   ```

   เปลี่ยนอีเมลตัวอย่างเป็นอีเมลจริง และตรวจสอบว่ามีเพียงบัญชีที่ตั้งใจไว้ได้รับสิทธิ์นี้ ห้ามสร้าง endpoint สาธารณะที่ยกระดับผู้สมัครคนแรกเป็นแอดมิน
5. ให้แอดมินปักหมุดสถานที่ทำงานจริงและตั้งรัศมีที่เหมาะสมก่อนอนุญาตให้บุคลากรลงเวลา
6. รวม/รักษา LINE routes เดิม, ตรวจ CORS และทดสอบ login, register, GPS geofence, check-in/out, leave, admin approval, password reset และ CSV export กับบัญชีทดสอบก่อน deploy
7. ตรวจสอบว่า GitHub Pages ชี้ไปยัง branch ที่ตั้งใจใช้งาน และตรวจผลหลัง deploy

## การรีเซ็ตรหัสผ่าน

หน้า “ลืมรหัสผ่าน” สร้างคำขอในฐานข้อมูล ไม่ได้ส่งอีเมลอัตโนมัติ เนื่องจากยังไม่มีผู้ให้บริการอีเมลที่ตั้งค่าไว้ ผู้ดูแลต้องตรวจสอบตัวตนผู้ขอผ่านช่องทางที่เชื่อถือได้ก่อนกดออก temporary password รหัสชั่วคราวแสดงเพียงครั้งเดียวและต้องส่งให้เจ้าของบัญชีผ่านช่องทางที่ยืนยันตัวตนได้

## ข้อจำกัดที่ยังต้องทราบ

- การตรวจ GPS เป็น geofence จากพิกัดที่เบราว์เซอร์ส่งมา จึงไม่ใช่หลักฐานป้องกันการปลอมตำแหน่งได้สมบูรณ์ ควรใช้การตรวจสอบขององค์กรเพิ่มเติมหากต้องการระดับความปลอดภัยสูง
- หน้ารายงานดาวน์โหลดรายการล่าสุดตามขีดจำกัด API (สูงสุด 500 รายการในมุมมองผู้ดูแล) ยังไม่ใช่รายงานแบบแบ่งหน้า
- การแจ้งเตือนในหน้าบุคลากรเป็นรายการสถานะจากข้อมูลลงเวลา/คำขอลา ไม่ใช่ push notification แบบเรียลไทม์
- บทบาทหัวหน้างานยังไม่มีโครงสร้างกำหนดผู้ใต้บังคับบัญชา จึงไม่เปิดเมนูอนุมัติคำขอลาสำหรับบทบาทนี้
- การเปลี่ยนรหัสผ่านจะยกเลิก token เดิม ผู้ใช้ต้องเข้าสู่ระบบใหม่
- ไฟล์ Worker ใน branch นี้ยังไม่ถูก deploy และ PR ยังไม่ถูกรวมเข้ากับ `main`

## การทดสอบเบื้องต้น

ตรวจ syntax ของ `app.js` และ `cloudflare/worker.js` แล้ว แต่ยังต้องทดสอบ end-to-end หลังรวม Worker routes เดิมและตั้งค่า secret/บัญชีแอดมินครบถ้วน
